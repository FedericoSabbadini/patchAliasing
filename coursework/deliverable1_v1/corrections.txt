Please revise Deliverable 1 to clarify several aspects of the planned work and resubmit the updated version before proceeding.
 
In light of the complexity of the coursework, you are allowed 2000 words for Deliverable 1.
 
 
Structure and organization
 
The overall structure could be improved to make the proposal easier to follow.
 
* Consider moving the Domain Description before Purpose and Scope, since it provides the application context.
* The Intended Audience section could be shortened or integrated elsewhere to save space.
* Significance and Impact would fit better after the project outline, once the reader understands what you intend to do.
* We also recommend adding a dedicated Data section, rather than describing datasets and data generation across multiple sections.
 
 
Mathematical formulation and hypotheses
 
The mathematical problem should be stated more explicitly. Since the project focuses on formally characterising structural aliasing, we would expect the proposal to outline the intended mathematical formulation. For example, introduce the tokenisation operator, indicate the conditions under which two signals become indistinguishable after tokenisation, and describe the theoretical conditions leading to structural aliasing. A complete derivation is not required at this stage, but the intended mathematical framework should already be clear.
 
Similarly, the current hypotheses read more like project objectives. We recommend reformulating them as explicit hypotheses (e.g., H1, H2, H3) that can be tested experimentally later.
 
 
Experimental methodology
 
The description of the MDL probing experiments is currently rather generic. Please explain more precisely:
 
* what representations will be probed;
* which metrics will be used;
* how different decoder layers will be compared; and
* how the results will be interpreted with respect to the stated hypotheses.
 
The experimental pipeline could also be simplified. A natural progression would be to first validate the theoretical predictions using clean synthetic sinusoids, identify the architectural blind spots, and only then move to the photovoltaic dataset as an application case.
 
 
Patch stride experiments
 
The proposal should clarify whether changing the patch stride requires retraining Chronos. If so, you should first verify that you can faithfully reproduce the original training procedure (training algorithm, configuration, hyperparameters, etc.), since otherwise comparisons across stride values may be difficult to interpret.
 
If you decide to study different stride values, we also suggest exploring values on both sides of the default configuration rather than only considering values below it. For example, either a broader symmetric range (e.g., 8, 10, 12, 14, 16, 18, 20, 22, 24) or a smaller symmetric subset (e.g., {8,16,24} or {10,16,22}) would provide a more balanced experimental design.
 
 
Bayesian analysis
 
The proposal mentions Bayesian statistics, but the intended analysis remains quite general. A brief description of the planned priors would strengthen this part of the proposal.
